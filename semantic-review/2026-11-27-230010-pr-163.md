# Portable app-settings in backup/import (pass 3)

This is a third-pass review following two rounds of reviewer fixes and one round of Kiro fixes applied in this session. The PR adds an `appSettings` section to the JSON backup format (bumping it to version 2), applies settings through a single atomic DataStore edit on import, implements a Room snapshot/rollback for replace mode, and surfaces `settingsApplied` in the success toast.

**Watch for:** The merge-mode DataStore failure path remains intentionally unrollback-able — the comment documents this, but the failure path (`throw dsErr`) surfaces only the DataStore error, not a hint that upserted rows remain in Room. Users who see "Import failed" in merge mode don't know their data was partially applied. The double-failure path (rollback also fails) now throws a compact `IllegalStateException` ("Import failed: settings write error and database rollback also failed. App data may be in a partially-imported state.") with the original DataStore error as cause, which the ViewModel displays as a toast.

**Verdict**: APPROVED

---

## High-level view

The settings portability boundary is enforced at three layers: DTO structure (fields simply don't exist), `buildBundle` (never reads secrets or device-bound fields from `AppSettings`), and `mergeSettings` (uses `current.copy`, so excluded fields come from the current device's settings, not the backup).

The import write sequence is: validate bundle → compute `mergedSettings` → snapshot Room (replace mode) → Room transaction → `applyPortableSettings`. Validation gates before any writes; settings computation gates before the Room snapshot, so a bad settings section can't partially commit Room.

The two-layer validate+clamp design (`validateBackupBundle` rejects at import, `mergeSettings` clamps defensively for direct callers) is now documented explicitly. This was the main source of reviewer confusion in earlier passes; the KDoc now makes the intent clear.

The rollback double-failure case now throws `IllegalStateException` with a "partially-imported state" message rather than silently rethrowing only the DataStore error. The ViewModel's `.onFailure` handler passes `err.message` directly to `showToast`, so users will see the compound message. It's long for a toast (~150 chars including "Cause: ...") — worth considering whether the toast should truncate or use a dialog for this case.

The 15 unit tests cover the codec pipeline thoroughly. The two new tests added in this session close the remaining gaps: `settingsBackupFullPipelineAllPortableFieldsReachMergedSettings` traces all 13 fields from `buildBundle` through `encodeJson`/`decodeJson`/`mergeSettings` to the final `AppSettings`; `settingsBackupRollbackDoubleFailureProducesCompoundExceptionMessage` pins the exception shape. The rollback data-flow test (`settingsBackupRollbackSnapshotDataShapeIsCorrect`) is acknowledged as a shape test only, with a comment noting that an integration test with real Room would go in `androidTest`.

<summary>Issues (2)</summary>

1. **Merge-mode DataStore failure leaves upserted rows without user notice** — When `replaceExisting = false` and `applyPortableSettings` throws, the upserted rows remain and `throw dsErr` is rethrown. The ViewModel shows "Import failed: [DataStore error]". The comment in `HordecraftRepository` documents this as intentional, but the user has no way to know their data was partially applied. Consider adding a note to the error message in this specific path, or documenting it in user-facing help text.

2. **Merge-mode DataStore failure also discards import counts** — In the same path, the exception is thrown before `DatabaseSyncCounts` is constructed, so the row counts (prompts, images, defaults) are discarded. The user can't see "N prompts were imported, settings failed" because the counts are never computed. If the merge-mode partial-state message is addressed, the counts should come from the entities lists computed earlier, not from the unreachable `DatabaseSyncCounts` construction.

### Toast length for the compound rollback error

The ViewModel's `importDatabase` failure handler is:

```kotlin
.onFailure { err ->
    showToast("Import failed: ${err.message ?: "Invalid backup file"}")
}
```

For the double-failure path, `err` is the `IllegalStateException` with message:

```
Import failed: settings write error and database rollback also failed. App data may be in a partially-imported state.
```

This is ~115 chars, which may clip on small screens. The DataStore error that caused the failure is available via `err.cause?.message` but is not surfaced in the toast — the original `dsErr` is now the cause of the compound exception, so a developer examining logs can still trace the root cause. The toast text itself is user-readable and actionable without the technical DataStore detail.

### Merge-mode partial state on DataStore failure

The comment in `importDatabaseFromUri` says:

> In merge mode (no snapshot) a DataStore failure after a successful Room upsert leaves the upserted rows in place. The additive nature of a merge means partial state is recoverable on retry; a rollback attempt is not warranted.

This is confirmed (possible): the `throw dsErr` path is reached if `mergedSettings != null` and `roomSnapshot == null` (merge mode). The user sees "Import failed: [DataStore error]" with no indication that their prompt history / saved images / model defaults were actually imported. A second import attempt will upsert the same rows again (idempotent), so the data is not lost — but the user experience is confusing. No code change is strictly required, but the toast could distinguish "data imported, settings not applied" from "nothing imported" for this path.

### Merge-mode DataStore failure discards counts and leaves silent partial state

No test for the merge-mode DataStore failure path (upserted rows remain, `settingsApplied = false`, `DatabaseSyncCounts` returned by... actually, in this path the exception is rethrown before `DatabaseSyncCounts` is constructed, so the counts are lost too). The behavior is: Room succeeds, DataStore fails, counts are discarded, ViewModel shows "Import failed". This is confirmed from reading the code — the `DatabaseSyncCounts` construction is after the `if (mergedSettings != null)` block, which throws, so the success path is never reached.
