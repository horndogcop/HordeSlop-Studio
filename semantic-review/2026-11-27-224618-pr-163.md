# Portable app-settings in backup/import

This PR adds an `appSettings` section to the existing JSON backup format, bumping it to version 2. Import applies settings through a single `applyPortableSettings` DataStore edit, addressing the atomicity complaint from the first reviewer pass. The rollback machinery — a Room snapshot taken before the write, restored if DataStore fails — is a genuine improvement over the initial draft.

**Watch for:** The Room→DataStore write sequence is still not atomic in the user-visible sense: Room can succeed while DataStore's `IOException` triggers the rollback path, but that rollback itself can silently fail, leaving the user with new DB data and old settings — or old DB data and no message. A second gap: coerce/clamping in `mergeSettings` and `applyPortableSettings` means out-of-range values from a hand-crafted backup are silently adjusted rather than rejected, so `validateBackupBundle` doesn't cover all invalid states it claims to. The ViewModel discards `settingsApplied` entirely, so users never learn whether their settings were restored.

**Verdict**: NEEDS_CHANGES

---

## High-level view

`AppSettingsBackupDto` contains 13 fields that match the 13 written in `applyPortableSettings`; secrets and device-bound fields are absent from the DTO entirely.

The write sequence during import is: validate bundle → compute `mergedSettings` → snapshot Room (replace mode only) → Room transaction → `applyPortableSettings`. This ordering prevents a bad settings section from causing a partial Room write. What it does not prevent is the inverse: Room succeeding, DataStore failing, and the rollback attempt also failing — leaving the user in an inconsistent state with no feedback beyond the generic "Import failed" toast.

The enum `fromKey` helpers all fall back to defaults on unknown strings (`entries.firstOrNull { ... } ?: DEFAULT`), so a backup produced by a future app version with new enum variants will silently downgrade values on restore. `validateBackupBundle` does not check enum fields at all, so the validation pre-flight cannot distinguish "unrecognised nav layout from a future version" from "corrupt value that should be rejected."

The rollback for the DataStore failure case is best-effort: the inner `runCatching` around the Room rollback transaction swallows any rollback failure without logging or surfacing it. If the rollback fails, the user ends up with new DB data and old settings, with no indication anything went wrong beyond the rethrown DataStore error.

`settingsApplied` in `DatabaseSyncCounts` is populated correctly by the repository, but `MainViewModel.importDatabase` builds the success toast from `counts.promptHistoryCount`, `counts.savedImagesCount`, and `counts.modelDefaultsCount` only — `settingsApplied` is never read. Users have no way to confirm their settings were restored.

The 11 new unit tests cover the pure-logic surface well (round-trip, secrets absent from JSON, merge-preserves-secrets, v1 compat, unknown-fields tolerance, URL/styles edge cases, replace-mode isolation). What is entirely missing is any test of the rollback path, the rollback failure path, the `validateBackupBundle` → `importDatabaseFromUri` gating integration, and cross-store state consistency.

<details>
<summary>Issues (6)</summary>

1. **Silent rollback failure on DataStore error** — The inner `runCatching` around the Room rollback in the DataStore `.onFailure` handler swallows rollback exceptions without logging. If the rollback transaction fails, the app is left with new DB data and old settings, no message to the user. At minimum, log the rollback failure; better, surface a distinct error message indicating partial state.

2. **Validation doesn't cover enum fields** — `validateBackupBundle` checks `globalRateLimitSeconds`, `galleryColumns`, and primary keys, but not `navLayout`, `generateButtonPlacement`, or any other string-keyed enum. An unrecognised value silently falls back to the default on `fromKey`; validation claims to reject bad backups before any writes but doesn't cover this class of invalid input. Consider whether unknown enum strings should be treated as a validation error or documented as acceptable (silent default).

3. **Validation coerces rather than rejects out-of-range numerics** — `mergeSettings` already clamps `globalRateLimitSeconds` and `galleryColumns`. `validateBackupBundle` then rejects the same range. This is redundant and potentially misleading: if the DTO arrives from JSON with `galleryColumns: 7`, the validator throws — but `mergeSettings` would have silently clamped it to 6. The two functions need a consistent policy: either validate-then-apply (validator rejects, merge never clamps) or apply-with-clamping (validator doesn't duplicate the clamping check). Right now they disagree on what "valid" means.

4. **`settingsApplied` is never surfaced to the user** — `MainViewModel.importDatabase` reads `counts.promptHistoryCount`, `counts.savedImagesCount`, and `counts.modelDefaultsCount` for the success toast but ignores `settingsApplied`. A user restoring a backup that includes settings has no confirmation that settings were applied. Update the toast to include "settings restored" when `settingsApplied` is true.

5. **Rollback is skipped for merge mode** — `roomSnapshot` is only populated when `replaceExisting && mergedSettings != null`. In merge mode, if the DataStore write fails after the upsert transaction succeeds, there is no rollback attempt. The merge case may add rows that the user will not expect when they see "Import failed". This may be intentional (upserted rows in merge mode are additive and arguably not harmful to leave), but it is not documented.

6. **No test for the rollback path or rollback failure** — None of the 11 new tests simulate a DataStore write failure after a successful Room transaction, so the rollback branch and the silent-swallow of rollback errors are entirely untested. These are the highest-risk paths in the import flow.

<summary>Details</summary>

### Cross-store atomicity gap

Room and DataStore are independent stores with no shared transaction boundary. The PR acknowledges this and adds a snapshot-and-rollback mechanism for the replace case. The specific failure mode that remains unhandled is:

```
Room.withTransaction { deleteAll(); upsertAll(new) }  ← succeeds
applyPortableSettings(merged)                          ← throws IOException
  → rollback Room { deleteAll(); upsertAll(snapshot) } ← throws (swallowed)
  → original IOException rethrown
  → ViewModel shows "Import failed"
  → DB now has new data, settings have old data, snapshot is gone
```

The inner `runCatching` on the rollback transaction (confirmed at the `.onFailure` block in `importDatabaseFromUri`) discards the rollback error entirely. The rethrown DataStore error is what the ViewModel receives, so the toast says "Import failed: [DataStore error]", which is misleading because half the import actually succeeded.

The rollback mechanism captures history/defaults/images/jobs but has no DataStore counterpart. If the Room transaction itself fails, settings are never touched — that direction is safe. The gap is only Room-succeeds-DataStore-fails, as described above.

### `validateBackupBundle` scope and double-handling of numeric ranges

The validator runs before any writes and gates on format version, `globalRateLimitSeconds` range, `galleryColumns` range, and non-blank primary keys. It does not validate enum string fields (`navLayout`, `generateButtonPlacement`) — an empty string or a future-version value silently becomes the default on `fromKey`. Whether unknown enum strings should be a validation error or a documented silent-default is worth confirming with the issue author; right now the validator makes no claim either way, but its KDoc implies it covers "invalid" values in the DTO.

The numeric range handling is inconsistent between functions. `validateBackupBundle` rejects `galleryColumns: 7`, but `mergeSettings` would have silently clamped it to 6. If the validator runs first (as it does in `importDatabaseFromUri`), `mergeSettings` never sees an out-of-range value from an import. The two contracts should be documented explicitly: `validateBackupBundle` is the import gate; `mergeSettings` is defensive regardless of call site. Right now they disagree on what "valid" means.

### `settingsApplied` flow

`HordecraftRepository` sets `settingsApplied = true` only inside `.onSuccess` after `applyPortableSettings` completes (confirmed in the `runCatching` block). `MainViewModel.importDatabase` builds its success toast from `counts.promptHistoryCount`, `counts.savedImagesCount`, `counts.modelDefaultsCount` only — `counts.settingsApplied` is never read. The field is wired correctly through the data layer but dead at the UI layer.

### Test coverage gaps

The 11 tests cover the pure-codec path thoroughly. Missing:

- DataStore failure after successful Room transaction (rollback triggered).
- Rollback failure (inner `runCatching` silently swallowing).
- `importDatabaseFromUri` with a bundle that fails `validateBackupBundle` — confirming Room is not touched.
- Merge-mode import with DataStore failure — confirming the upserted rows remain (intentional) or are rolled back (if the intent changes).
- Post-import observation: a test that calls `importDatabaseFromUri` and then reads `settingsStore.settings.first()` to confirm the restored values are visible. This is what the second reviewer comment specifically calls out as missing.
